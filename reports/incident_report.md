## 2. Executive Summary

This incident was generated as part of a controlled malware detection and incident-response laboratory.

A harmless ransomware simulator was executed inside a Kali Linux virtual machine. The simulator operated only on dummy laboratory files located in:

```text
~/malware-lab/protected
```

The simulator renamed test files by adding the `.locked` extension and created a fake ransom note named:

```text
RANSOM_NOTE.txt
```

A Python-based detection script continuously monitored the protected directory. When suspicious files appeared, the detector generated security alerts and recorded them in:

```text
~/malware-lab/logs/alerts.log
```

The activity was then investigated using behavioral analysis. Evidence was collected, suspicious files were isolated, and clean laboratory files were restored.

No real ransomware, destructive malware, data theft, persistence, or system damage was involved.

---

# 3. Incident Description

The laboratory started with ten harmless test documents:

```text
document_1.txt
document_2.txt
document_3.txt
...
document_10.txt
```

The ransomware simulator modified these files by renaming them:

```text
document_1.txt
        ↓
document_1.txt.locked
```

Similar modifications were performed against the remaining laboratory files.

The simulator also created:

```text
RANSOM_NOTE.txt
```

The note contained a message identifying the activity as a safe laboratory simulation.

---

# 4. Attack Simulation

## 4.1 Simulated Behavior

The simulator performed the following activities:

1. Located files in the protected laboratory directory.
2. Identified `.txt` test files.
3. Renamed the files with a `.locked` extension.
4. Created a fake ransom note.
5. Generated console output describing the simulated activity.

Example:

```text
document_1.txt
        ↓
document_1.txt.locked
```

The activity was designed to resemble a simplified ransomware file-modification pattern.

## 4.2 Safety Controls

The simulator did **not**:

* Encrypt files.
* Delete files.
* Spread to other systems.
* Establish persistence.
* Steal information.
* Modify the operating system.
* Attack external systems.

All activity remained inside the controlled laboratory directory.

---

# 5. Detection

## 5.1 Detection Mechanism

A Python detector monitored:

```text
~/malware-lab/protected
```

The detector compared the current directory contents against previously observed files.

It generated a **HIGH** alert when a file ending in:

```text
.locked
```

was detected.

It generated a **CRITICAL** alert when:

```text
RANSOM_NOTE.txt
```

was detected.

---

## 5.2 Detection Alerts

Example alerts generated by the detector:

```text
[HIGH] Suspicious ransomware indicator detected: document_1.txt.locked
[HIGH] Suspicious ransomware indicator detected: document_2.txt.locked
[HIGH] Suspicious ransomware indicator detected: document_3.txt.locked
[HIGH] Suspicious ransomware indicator detected: document_4.txt.locked
[CRITICAL] Ransom note detected
```

The alerts were stored in:

```text
~/malware-lab/logs/alerts.log
```

...

## 7.3 Behavioral Indicators

The following behavior was considered suspicious:

* Multiple files modified in a short period.
* Files renamed with a common `.locked` extension.
* Creation of a ransom-note file.
* Repeated file-system activity within the protected directory.

## 7.4 Analysis Conclusion

The observed activity was consistent with a simplified ransomware-like behavior pattern.

However, the activity was confirmed to be generated by the laboratory's harmless simulator rather than real ransomware.

# 15. Lessons Learned

The laboratory demonstrated several important cybersecurity concepts.

### Detection

Monitoring file-system activity can identify suspicious ransomware-like behavior.

### Behavioral Analysis

A large number of file modifications combined with a common extension and ransom-note creation can provide useful detection indicators.

### Evidence Collection

Security alerts and system information should be preserved during an investigation.

### Containment

Suspicious files should be isolated to prevent further activity.

### Recovery

Clean files should be restored after the threat has been contained.

### Documentation

A structured incident report helps explain:

* What happened.
* How it was detected.
* What evidence was collected.
* How the incident was contained.
* How recovery was performed.
